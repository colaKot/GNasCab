# 非管理员子账号权限方案

> 目标账号类型：`user`（非管理员）。⚠️ admin / super_admin 是**权限豁免**的（`hasPermission` 里直接 `return true`，`getValidPaths` 返回全部源目录），任何路径授权对它们无效。所以这个功能只对 `user` 类型生效，创建账号时不要选 admin。

## 一、三条需求的可行性速览

| 需求 | 现状 | 结论 |
|---|---|---|
| 1. 按目录授权，区分「可修改 / 只可访问」 | `user_permission` 表天然支持 | ✅ **已具备**，只差管理界面 |
| 2. 子账号只能用指定的几个应用 | 完全没有 | ❌ **需新建**（改动最大） |
| 3. 应用内只能看到授权目录的内容 | 主干列表接口**已经做了** | ⚠️ 主干已具备，但有几处「按 id 直取」的接口漏了，做不到「不论如何都无法看到」 |

---

## 二、现状：权限是怎么生效的

三层机制，理解它们才能判断改哪里：

**① 存权限** —— `user_permission(uid, res_type, res_path, action)`
`res_path` 是绝对路径，匹配时按**前缀**算（含子目录）。`res_type` 目前只有 `file` 一个值。

**② 判权限** —— `src/utils/permissionUtil.js` 的 `hasPermission(knex, user, action, resPath)`
数组形式的 action 是 **OR** 关系（`whereIn`），不是 AND。

**③ 列表过滤** —— 各媒体模块的 `getValidPaths(user)`
把「用户在 `user_permission` 里 `action='view'` 的路径」∩「`xxx_source` 的根目录」，得到可见根目录列表，然后在 SQL 层做 `path = ? OR path LIKE '前缀%'` 过滤，无权限时直接 `whereRaw('1 = 0')` 返回空集。

关键点：**媒体应用的可见性完全取决于你有没有 `view` 这个 action**，而且硬编码了 `res_type='file'`。这决定了下面权限档位怎么配。

## 三、需求 1：目录授权

### 数据模型（复用现有表，不新建）

```
user_permission
  uid       = 子账号 id
  res_type  = 'file'      ← 必须，各模块 getValidPaths 硬编码只认 'file'
  res_path  = 'E:\Media\Movie2'   ← 绝对路径，自动覆盖子目录
  action    = 见下表
```

### 两档权限映射

| 界面档位 | 落库的 action | 效果 |
|---|---|---|
| 只可访问 | `view` + `download` | 能在文件夹里浏览、能在影视/音乐/相册里看到并播放、能看缩略图、**能下载原文件**；不能上传、新建、重命名、移动、删除 |
| 可修改 | `view` + `download` + `update` + `delete` + `upload` | 全部放行（增删改查） |

对应到用户说的「增删改查」：

- 查 → `view`（列表可见性靠它）+ `download`（原图/原文件/下载按钮）
- 增 → `upload`（上传、新建文件夹、新建文件）
- 删 → `delete`
- 改 → `update`（重命名、编辑器保存、移动）

### ⚠️ 一个必须知道的细节

`view` 和 `download` 在播放类接口上是 **OR** 关系（`requirePermission(['download','view'])`），所以只给 `view` 也能正常播放和看图。

**已决策：只可访问档同时给 `download`**（用户 2026-10-01 确认）—— 只读档可以在文件管理里下载原文件。真正被卡住的只剩上传 / 新建 / 重命名 / 移动 / 删除类接口。

### 落库接口

已有现成接口，不需要新写服务端逻辑：

- `POST /api/user/permissions/get` —— 读某 uid 的权限列表
- `POST /api/user/permissions/:uid` —— **覆盖式**写入（先删后插）

⚠️ 覆盖式写入有两个坑：
1. 每次提交必须带**全量**权限，不能只传增量。
2. 同一个 action 下**父子路径不能并存**，会报 `permission.PATH_PARENT_EXISTS`。比如同时给 `E:\Media` 和 `E:\Media\Movie2` 的 `view` 会失败。界面需要在提交前做去重（父路径已存在就丢弃子路径）。

## 四、需求 2：应用白名单（全新）

### 为什么必须做在服务端

现在**完全没有任何「按用户限制可用应用」的机制**：

- `config.defaultApps` 是应用全集（22 个）。
- `config.normalUserNoShowApps` 按 `user.type` 全局砍掉几个图标，**只影响列表显示，不拦 API**。
- `userAppsHide` / `userAppsOrder` 是 per-uid 的，但只是**首页展示偏好**。
- 客户端首页列表来自登录响应缓存，点击图标是**纯本地路由跳转**，不问服务端。
- 唯一真正的模块级拦截是 scoped token 的 `allow_api`，但那只对 `scoped` 类型令牌生效，普通 `access` 令牌（也就是登录后的账号）**完全不校验**。

结论：不做服务端拦截，子账号只要直接调 HTTP API 就能用任意应用。

### 存储：不用建表

`tableConfig.getConfigByKey(key, uid)` 本身就支持按 uid 存（`config` 表有 `uid` 列）。直接新增两个 key：

```
key = 'userAllowedApps'   uid = <子账号 id>   value = '["folder","sync","movie","photo","music"]'
```

这样零建表、零迁移。

### 拦截：新增一个模块级中间件

在 `src/api/app.js` 挂载路由的地方加一层，思路：

```
白名单 = config 表读 userAllowedApps(uid)；为空 = 不限制（向后兼容）
公共 API 前缀（登录/首页/应用列表/消息/外观/硬件信息等）永远放行
其余请求：取 URL 前缀 → 查 appKey → 不在白名单里则 403
```

### appKey → API 前缀映射表（初稿，需核对）

| appKey | 界面名 | API 前缀 |
|---|---|---|
| `folder` | 文件夹 | `/api/file`、`/api/fileServer`、`/api/editor` |
| `movie` | 影视 | `/api/video`、`/api/videoPlayer` |
| `photo` | 相册 | `/api/photo`、`/api/mapApi` |
| `music` | 音乐 | `/api/music` |
| `sync` | 同步 | `/api/sync`、`/api/fileBackup` |
| `book` | 图书 | `/api/book` |
| `note` | 笔记 | `/api/notes` |
| `encrypted` | 加密空间 | `/api/encryptedSpace` |
| `share` | 分享 | `/api/quickShare` |
| `mounts` | 挂载 | `/api/fileMount`、`/api/openlistMount` |
| `media_tool` | 媒体工具 | `/api/mediaTool` |

必须**永远放行**的公共前缀：`/api/auth`、`/api/apps`、`/api/home`、`/api/message`、`/api/appearance`、`/api/hw`、`/api/user`（需拆分——改自己密码/2FA 要放行，管理他人用户要拦）、以及各类静态资源。

### 配套改动

- `appsService._getAllowedApps()` 叠加白名单，让 `GET /api/apps/getApps` 只下发白名单内的应用 —— 界面自然只显示这几个图标。
- 客户端（Flutter / 鸿蒙）**无需为「隐藏」做任何事**，但建议增加对 `403 APP_NOT_ALLOWED` 的处理，避免用户从别处跳进去看到一堆报错。

## 五、需求 3：应用内只能看到授权目录（主干已具备）

### 已经做好的部分（✅ 可以直接用）

| 应用 | 接口 |
|---|---|
| 影视 | `/video/list`、`/video/list/count`、`/video/home/data`、`/video/history/list`、智能相册预览 |
| 音乐 | `/music/list`、`/music/list/count`、`/music/album/list`、`/music/artist/list`、歌单预览、封面、转码流 |
| 相册 | timeline 全套（count/dates/years/photos）、人脸、地点、智能相册、相簿预览、回收站列表、地图打点 |
| 图书 | `/book/list`、`/book/list/count`、书单预览、历史、归档、封面 |
| 文件夹 | `/file/list`、`/file/search`、缩略图、原图、下载 |

也就是说 —— **你说的 Movie1 / Movie2 场景，在列表这一层已经是现成能力**：只给 Movie2 的 `view`，影视首页就只会出现 Movie2 的片子。

### 但做不到「不论如何都无法看到」的缺口

这些接口**没有做路径权限过滤**，属于「知道 id 就能拿到内容/路径」：

| 严重度 | 接口 | 问题 |
|---|---|---|
| 🔴 | `GET /api/videoPlayer/hls/:playId/:filename` | **整个路由连 `authenticateJWT` 都没挂**，未登录就能拉转码分片 |
| 🔴 | `GET /api/video/detail`、`/episodes`、`/tvPlayInfo`、`/discContents`、`/discContents/thumb` | 按自增 `index_id` 返回任意媒体的**绝对文件路径 + NFO 元数据**，无路径校验 |
| 🔴 | `/api/photo/collection/list`、`/api/book/collection/list` | 预览只按合集自己的 `path_list` 过滤，**不叠加用户权限**；而创建合集时也只校验「在某个源目录下」，不校验用户是否有权 → 可主动构造越权合集 |
| 🟠 | `/api/video/album/list`、`/api/music/collection/list`、`/api/video/collection/list` | 预览未叠加用户路径过滤，会泄露无权目录的绝对路径 |
| 🟠 | `POST /api/photo/trash/restore` | 零校验，枚举 id 就能恢复任意条目 |
| 🟠 | `POST /api/photo/trash/delete` | 磁盘删除逐条校验了，但**索引行是无条件全删** |
| 🟡 | `/api/video/favorite/*`、`/api/music/favorite/*` | 按 `index_id` 直接写，无路径校验（影响低） |
| 🟡 | `/api/videoPlayer/stop`、`/uploadSubtitle` | 仅登录，无路径校验 |

好消息：这些**全部可修**，因为 `video_index` / `music_index` / `photo_index` / `book_index` 都存了绝对路径列 `path`，复用现成的 `_applyXxxPathPrefixFilter()` 就行，属于「遗漏」而不是「做不到」。

### 实施中发现并修掉的三个既有缺陷

1. **覆盖式写权限被「伪冲突」挡住**（`userService.setUserPermissions`）
   历史实现在删除旧权限**之前**拿旧数据做父子冲突校验并抛 `permission.PATH_PARENT_EXISTS`。
   结果：「把已授权的父目录收窄成子目录」永远保存不了。覆盖式写入会先 `delete` 该 uid
   全部旧行，旧数据冲突是伪冲突 → 已移除该校验。

2. **同一 action 的路径去重用裸 `startsWith`**（同上文件）
   `'E:\MediaBackup'.startsWith('E:\Media')` 为 true，导致 `E:\MediaBackup` 的授权被静默丢弃。
   已改为带分隔符边界的 `_isPathUnder()`。

3. **客户端「解除应用限制」永远不生效**（`user_api_service.dart`）
   原实现 `if (allowedApps != null) body['allowed_apps'] = allowedApps;` —— 值为 null 时该键被省略，
   而服务端判定的是 `hasOwnProperty('allowed_apps')`，于是「关闭限制」成了空操作。
   已改为显式提交 `'allowed_apps': null`。
   同类陷阱：编辑器原先把「开启限制但一个都没勾」兜底成 null，而 null=`不限制`、`[]`=`全禁止`，
   语义正好相反 → 已改为保存前拦截并提示。

### 使用方式

1. 用 super_admin 登录，创建类型为 `user` 的子账号。
   ⚠️ **不要选 admin** —— admin / super_admin 在 `hasPermission` 里直接 `return true`，任何授权都不生效。
2. 用户管理 → 选中该子账号 → 权限设置。
3. 打开「限制可用应用」→ 勾选：文件管理 / 同步 / 影视 / 照片 / 音乐。
   （`文件管理` 的 appKey 是 `folder`，同时承载「快速上传」「下载中心」的接口）
4. 「添加授权目录」→ 选目录 → 每个目录选「只可访问」或「可修改」。
5. 保存。子账号重新登录后生效（白名单缓存 3 秒内自动失效）。

### 已知边界

- 未在 `APP_API_PREFIXES` 登记前缀的应用（`upload` / `download` / `task_center` / `monitor` /
  `terminal` / `process` / `photo_backup` / `user` 等）无法在 HTTP 路径层拦截，
  主要靠「不下发图标」实现隔离。若需强隔离，应先给它们分配独立 API 前缀。
- 同目录的「只读 / 可写」是**按 action 粒度**落库的：`E:\Media` 给只读、`E:\Media\Movie2` 给可写时，
  父子并存会由服务端自动去重（同 action 保留父路径），可写权限仍会生效。
